# GPU 核心目录与显存绑定

## 规则

- 核心表示完整商业型号，不是芯片裸片编号。大小写、空格归一化，例如 `rTx 4070 Ti` → `RTX4070TI`，ID 为 `GPU-NVIDIA-RTX4070TI`。
- 核心与显存分层：一个核心可绑定多个容量、显存类型或修订规格。规格 ID 包含核心、容量、类型及可选修订。
- 商品必须选择核心和属于该核心的显存。单规格自动选择，多规格显式选择；换核心清空不兼容显存。
- 行情仍只有核心基础买入/卖出价，不按显存、成色、质保、盒子或商品拆价，不填写报价来源，不同步修改商品价格。
- 官方目录包含 NVIDIA 桌面 GeForce 30/40/50 系列 28 个核心、36 个规格，包括 D/V2、GDDR6/GDDR6X 和 OEM 修订。笔记本、专业卡不冒充这套标准目录。
- 标准目录来自 `src/data/gpuCoreCatalog.ts` 中记录的官方资料；这是参考配置，不创建库存、商品或行情业务记录。
- 管理员可在选择核心时新建；商品场景要求显存，行情场景允许先建空规格核心。门店新增规格标为非标准，不能覆盖官方规格。
- 新建在原弹窗内切换步骤，不叠加创建弹窗。返回时保留父表单草稿。核心保存成功即存在，随后取消商品不会删除核心。
- 原有商品不批量改写：只提供识别建议，需要人工确认。未知显存类型或同容量 OEM 修订歧义保持待确认。
- 已关联业务的模板禁止修改核心/显存，导入和按 ID 更新也不能绕过。旧库存、历史单据和资金事实不改写。

## 持久化与权限

- 标准目录只读；门店扩展写入 `gpu_core_catalog`，主键 `(tenant_id, store_id, id)`，相同核心 ID 可在不同门店各自维护。
- 迁移 `server/migrations/010_gpu_core_catalog.sql` 仅增加表和迁移记录。初始化器与生产预检纳入 `gpu-core-catalog-v1`。
- 接口：GET `/api/gpu-cores`、POST `/api/gpu-cores`、POST `/api/gpu-cores/:id/specs`。
- 读取需要商品/行情/开单/库存权限之一，维护需要老板或权限管理入口权限。服务端强制校验，不靠隐藏按钮授权。
- 写入沿用现有串行事务、CSRF、幂等和审计。幂等指纹含门店，丢失响应后同一内容重试复用身份；不同内容换身份。SQL 保存失败还原内存并释放请求声明。
- 前端以已提交的返回结果更新目录，不用第二次读取成功与否判断写入成败。
- 上线时需本地构建、正常备份/预检/回滚流程，本次开发不连接生产。代码回滚保留新增表，不删除门店目录数据。

## 本地验收

- 单元覆盖核心归一化、多显存、OEM 歧义、官方不可覆盖、关联模板/导入保护、保存失败还原。
- 隔离 PostgreSQL HTTP 验收覆盖权限、重复请求、跨门店同 ID、跨核心规格拒绝、真实商品绑定，以及目录写入不改变库存/报价/资金事实。
- 真实本地 API 页面检查桌面创建、手机选择/新增/返回草稿、375/390/430px 尺寸；不以浏览器模拟替代 iPhone 真机键盘和硬件验收。
- 浏览器直接进入深链接后后退可离开整个文档；层内返回使用现有返回入口，路由内返回使用现有手机返回规则，不额外改写全局历史。
- 本次仅本地开发，未合并、推送或上线。
